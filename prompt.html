# Task: เพิ่ม Sample Plan Trigger ใน Quality Module

## Context
- ระบบ: Herbal Medicine ERP — Next.js App Router + Tailwind + React 18
- หน้าที่แก้: `app/quality/qc-entry/page.tsx` (และ component ย่อย)
- URL จริง: https://herbal-erp-more.bmscloud.in.th/quality/qc-entry
- ปัญหาตาม audit: "ยังไม่มีการแจ้งเตือน เมื่อ lot รับเข้าหรือ WO complete ต้องสร้าง manual"

## Acceptance Criteria

### 1. Backend / API
- เพิ่ม table `qc_pending_tasks` (Prisma schema หรือเทียบเท่า) ฟิลด์:
  - id, triggerType ('gr' | 'wo' | 'stability' | 'complaint')
  - title, productCode, lotNumber, sourceRef
  - dueDate, priority ('critical' | 'high' | 'medium' | 'low')
  - createdAt, status ('pending' | 'converted' | 'dismissed')
  - assignedTo (optional, user id)
- เพิ่ม endpoint:
  - GET  /api/quality/pending-tasks
  - POST /api/quality/pending-tasks/[id]/convert  → mark converted + return prefill
  - POST /api/quality/pending-tasks/[id]/dismiss

### 2. Event triggers (background jobs / webhooks)
สร้าง task อัตโนมัติเมื่อ:
- **gr** : Goods Receipt → lot สถานะเป็น 'quarantine' (listen `inventory.lot.received`)
- **wo** : Work Order complete → FG lot เข้า quarantine (listen `production.wo.completed`)
- **stability** : Cron job รายวัน — เช็ค stability_schedule แล้วสร้าง task เมื่อถึง time point ±3 วัน
- **complaint** : Customer complaint API → severity ≥ medium

### 3. Frontend
- เพิ่ม `` ที่หัวของ qc-entry list (ใต้ breadcrumb เหนือ filter chips)
- ออกแบบเป็นการ์ดเหลือง collapsible พร้อม badge จำนวน
- แต่ละ task แสดง: triggerType icon, title, product/lot/sourceRef, dueDate, priority chip
- ปุ่ม 2 อัน: "▶ ลงทะเบียน" (convert → navigate ไป /quality/qc-entry/new พร้อม prefill query params),
              "✕ ปิด" (dismiss task)

### 4. Reference UI
ดูตัวอย่างได้ที่ prototype: `qc-entry.html` → component `PendingTasksPanel`
(โครงสร้าง state + styling พร้อมใช้ — แค่ port มา TypeScript + เชื่อม API จริง)

### 5. Definition of Done
- [ ] DB migration + seed default 4 demo tasks
- [ ] 4 trigger events ทำงานครบ (มี integration test)
- [ ] Panel แสดงผลถูกต้อง + responsive
- [ ] Convert action ส่ง prefill ไปหน้า new ถูก
- [ ] Dismiss action soft-delete (ไม่ลบจาก DB)
- [ ] Audit log ทุก action

### 6. Out of Scope
- ไม่ต้องทำ email/SMS notification (ใช้ in-app เท่านั้น)
- ไม่ต้องทำ assignment workflow (เก็บ assignedTo field ไว้ก่อน)

# Task: เพิ่ม Retain Sample Storage ใน QC Entry

## Context
- ระบบ: Herbal Medicine ERP — Next.js App Router + Tailwind
- หน้าที่แก้: `app/quality/qc-entry/new/page.tsx` (หรือ form component)
- ปัญหาตาม audit: "ไม่มีคลังสำหรับตัวอย่างเก็บรักษา ไม่มี storage location ของ sample"

## Acceptance Criteria

### 1. Master Data
- เพิ่มคลัง 4 แห่ง (ใน warehouse master):
  - WH-RETAIN-01 — Retain Room (อุณหภูมิห้อง 15-30°C)
  - WH-RETAIN-02 — Retain Cold (2-8°C)
  - WH-RETAIN-03 — Stability Chamber 25°C / 60%RH
  - WH-RETAIN-04 — Stability Chamber 40°C / 75%RH
- เพิ่ม category `retain` ใน warehouse_type enum

### 2. DB schema
ที่ table `qc_samples` เพิ่ม:
- retainStorageId (FK → warehouse.id, nullable)
- retainShelf (string, e.g. "A-12")
- retainExpiry (date) — ต้อง ≥ lot expiry + 1 year (FDA 21 CFR 211.170)
- retainQty (number) — แยกจาก test quantity

### 3. Frontend (Form)
ใน NewSampleForm:
- โผล่ section "📦 Retain Sample Storage" สีม่วงเมื่อ bufferQty > 0
- ฟิลด์:
  - Dropdown คลังเก็บ (4 ตัวเลือกจาก master data)
  - Input ชั้นวาง (text, validation: format A-NN)
  - Date picker หมดอายุ retain (default = lot.expDate + 1 year)
- มี hint: "Retain sample ต้องเก็บ ≥ 1 ปีหลัง expire ของ lot (FDA 21 CFR 211.170)"

### 4. Stock Movement
เมื่อ confirm sample entry:
- ตัด stock จาก lot quarantine (test qty + retain qty)
- สร้าง 2 movement transactions แยก:
  - `test_consumption` → ไป QC Lab
  - `retain_storage` → ไปคลัง retain ที่เลือก
- ผูก reference: sampleId

### 5. Retain Inventory View
สร้างหน้าใหม่ `/quality/retain-inventory`:
- Table แสดง retain samples ทั้งหมด
- Filter: คลัง / สถานะ (active/expired) / product
- Action: "destroy" (เมื่อถึงวันหมดอายุ retain — log audit trail)

### 6. Reference UI
prototype: `qc-entry.html` → ใน NewSampleForm มี section สีม่วง "Retain Sample Storage"

### 7. Definition of Done
- [ ] DB migration + seed 4 warehouses
- [ ] Form validation (ต้องเลือก storage ถ้า bufferQty > 0)
- [ ] Stock movement สร้าง 2 transactions แยก
- [ ] Retain inventory page list + filter
- [ ] Expire alert (notification when retain reaches expiry)

แยก stage Released เป็น 2 ขั้น: QC Released → Warehouse Verified เพื่อให้คลังตรวจนับสินค้าจริงก่อนปล่อยเข้าระบบขาย 

# Task: Dual Approval — QC Release + Warehouse Verify

## Context
- ระบบ: Herbal Medicine ERP — Next.js App Router + Tailwind
- หน้าที่แก้: `app/quality/qc-entry/[id]/page.tsx` + Work Order release logic
- ปัญหาตาม audit (ระบุชัด):
  > "ปุ่ม released เป็นใครก็ได้กด ไม่มีการตรวจสอบจำนวนก่อนปล่อยเข้าคลัง"
  > "การอนุมัติปล่อยผ่านสินค้าต้องมาจาก QC จากฝ่าย QC และสถานะ release ใน lot
  >  เป็นฝ่ายคลัง ที่ตรวจนับสินค้าก่อนกด released ปล่อยสินค้าเข้าคลัง"

## Acceptance Criteria

### 1. DB schema
ที่ table `qc_samples` (หรือ lot):
- เปลี่ยน enum status: เพิ่ม 2 values
  - 'qc_released'   (QC อนุมัติแล้ว รอคลังตรวจ)
  - 'wh_verified'   (คลังตรวจนับแล้ว — lot พร้อมขาย)
- เพิ่ม fields:
  - qcReleasedBy (FK user), qcReleasedAt (timestamp)
  - whVerifiedBy (FK user), whVerifiedAt (timestamp)
  - whCountVerified (number) — จำนวนที่คลังนับได้จริง
  - whCountExpected (number) — จำนวนที่ QC ระบุ
  - whCountDiff (number) — diff = verified - expected
  - whVerifyNote (text) — เหตุผลถ้า diff != 0

### 2. RBAC / Permissions
- Role `qc_manager` เท่านั้นที่กด QC Release ได้
- Role `warehouse_supervisor` เท่านั้นที่กด Warehouse Verify ได้
- ตรวจสิทธิ์ทั้งฝั่ง frontend (hide button) + backend (validate)

### 3. Status Flow
```
Registered → Draft → In Progress → Approved
                                      ↓
                                QC Released  (by QC)
                                      ↓
                                WH Verified  (by Warehouse)
                                      ↓
                                Lot status = 'released'
```
- Lot สามารถใช้ในระบบขาย/ส่งสินค้าได้ก็ต่อเมื่อ wh_verified แล้วเท่านั้น
- ก่อน wh_verified — lot ยังถือว่าอยู่ในสถานะ quarantine

### 4. Frontend
ในหน้า qc-detail:
- Status bar เพิ่มเป็น 6 nodes:
  ① Registered → ② Draft → ③ In Progress → ④ Approved → ⑤ QC Released → ⑥ WH Verified
- ปุ่ม footer เปลี่ยนตาม role + stage:
  - Approved + role=qc_manager  → ปุ่ม "QC Release ✓"
  - QC Released + role=warehouse  → ปุ่ม "Warehouse Verify ✓"
  - WH Verified → label "✓ Released ครบ 2 ขั้น"
- Modal warehouse verify ต้องมี:
  - Input "จำนวนนับจริง" (whCountVerified)
  - แสดง diff vs expected
  - ถ้า diff != 0 → require note (เหตุผล)

### 5. Audit Trail
- log ทุก state transition: who/when/note
- Immutable — ไม่ allow edit history

### 6. Reference UI
prototype: `qc-detail.html` → StatusBar (6 nodes), footer (2 buttons), submitOpen modal

### 7. Definition of Done
- [ ] DB migration (alter enum + add columns)
- [ ] RBAC ทำงานทั้ง 2 ฝั่ง (FE + BE)
- [ ] Warehouse verify ต้องกรอกจำนวนจริง
- [ ] Diff > 0 → require note + flag ใน audit
- [ ] Lot quarantine release = wh_verified เท่านั้น (เช็คทุก consumer)
- [ ] Notification ส่งหา warehouse role เมื่อ QC release
- [ ] Test: user ที่ไม่มี role กดปุ่มไม่ได้ (403 จาก API)

# Task: Auto-notification System (Cross-department)

## Context
- ระบบ: Herbal Medicine ERP — Next.js App Router
- ปัญหาตาม audit: "ไม่มีการแจ้งเตือนอัตโนมัติไปยัง QC เมื่อฝ่ายผลิต complete batch
                   หรือฝ่ายคลังรับ lot เข้า"

## Acceptance Criteria

### 1. DB schema
table `notifications`:
- id, recipientUserId (or recipientRole), kind, title, message
- relatedEntity (polymorphic: sample/lot/wo/complaint)
- relatedId, link (URL ไปยังหน้าที่เกี่ยวข้อง)
- read (boolean), readAt (timestamp)
- createdAt
- priority ('info' | 'warn' | 'critical')

### 2. Backend events to listen
สร้าง notification เมื่อ:

| Event                              | Recipient role       | Title                           |
|------------------------------------|----------------------|---------------------------------|
| inventory.lot.received             | qc_operator          | 🆕 Lot รับเข้าใหม่ต้องตรวจ      |
| production.wo.completed            | qc_operator          | 🏭 WO Complete — รอ QC          |
| stability.timepoint.due (3 day)    | qc_operator          | 🕐 Stability ครบกำหนด           |
| complaint.created                  | qc_manager           | ⚠️ Customer complaint ใหม่      |
| qc_sample.qc_released              | warehouse_supervisor | ⏳ รอ Warehouse Verify          |
| qc_sample.wh_verified              | qc_operator, sales   | 🎉 Lot release ครบทั้ง 2 ขั้น   |
| qc_sample.oos_detected             | qc_manager, qa_head  | 🚨 OOS Investigation required   |
| ipc.deviation.created              | qc_manager           | ⚠️ IPC Deviation                |

### 3. API
- GET  /api/notifications?unreadOnly=true&limit=20
- POST /api/notifications/[id]/read
- POST /api/notifications/read-all
- WebSocket / Server-Sent Events endpoint: /api/notifications/stream (push real-time)

### 4. Frontend Components

#### a) NotificationBell (header — global layout)
- Bell icon + red badge (unread count, "9+" if > 9)
- Click → dropdown panel (right-aligned, 320px wide)
- Panel:
  - Header: "การแจ้งเตือน" + ปุ่ม "อ่านทั้งหมด"
  - List items: priority dot, title, message, "เมื่อ X นาทีที่แล้ว"
  - Click item → mark read + navigate ไป link
  - "ดูทั้งหมด →" footer link ไปหน้า /notifications

#### b) Toast (global)
- Position: bottom-right
- Auto-dismiss 4 วินาที (10 วินาทีถ้า critical)
- Stack ได้ (multiple toasts)
- Animation: slide-in from bottom

#### c) Full notifications page
- /notifications — list ทั้งหมด, filter by kind/priority, mark read/delete

### 5. Real-time (WebSocket หรือ SSE)
- ทุก client เปิด connection หลัง login
- เมื่อมี notification ใหม่ → push ลง bell + show toast ทันที
- Reconnect logic + heartbeat

### 6. Reference UI
prototype: `qc-entry.html` → `NotificationBell` + `Toast` components

- [ ] DB schema + indexes (recipientUserId + read + createdAt)
- [ ] Event listeners ครบ 8 events
- [ ] Bell badge update real-time
- [ ] Toast แสดงเมื่อมี event ใหม่
- [ ] Mark read sync ทุก device ที่ login user เดียวกัน
- [ ] Performance: notification fetch < 100ms (P95)
- [ ] Cleanup job: ลบ notification > 30 วันที่ read แล้ว
